# 용어 작성 가이드

## 파일

| 파일 | 내용 |
|---|---|
| `src/content/terms/<id>.json` | 용어 1개. 파일 이름이 id이고 URL이 된다 (`/terms/wrc-plus/`). |
| `src/content/stubs.json` | 준비 중 용어 목록. |
| `src/content/ladders.json` | 사다리 목록. 적힌 순서대로 홈에 나온다. |

스키마는 `src/lib/schema.ts`에 zod로 정의돼 있다. 이 문서와 스키마가 다르면 둘 다 고친다.

## 스키마 (`src/content/terms/<id>.json`)

| 필드 | 필수 | 내용 |
|---|---|---|
| (파일 이름) | 예 | id. kebab-case (`wrc-plus.json`, `attack-angle.json`). 파일 안에는 `id`를 쓰지 않는다. |
| `abbr` | 예 | 표제어. 영문 약어나 이름 (`wRC+`, `Attack Angle`). |
| `chip` | 예 | 사다리·링크에 쓰는 짧은 표기. 한국어가 더 익숙하면 한국어 (`배럴`, `블라스트`). |
| `ko` | 예 | 한국어 이름. |
| `en` | 예 | 영문 정식 이름. |
| `aliases` | 아니오 | 검색용 별칭. 한글 발음, 붙여쓰기, 관련 하위 지표 이름. |
| `level` | 예 | 1 입문, 2 중급, 3 심화. |
| `order` | 예 | 같은 레벨 안에서의 순서. 작을수록 앞이다. 전체 용어 목록과 홈 입구에 이 순서로 나온다. 10 단위로 매겨 사이에 끼워 넣을 자리를 둔다. |
| `cats` | 예 | `타격`, `투구`, `수비`, `종합`, `트래킹` 중 하나 이상. |
| `added` | 아니오 | 처음 공개된 해. 값이 있으면 ‘N년 등장’ 배지가 붙고 홈의 ‘이미 안다면’에 먼저 나온다. 최근(2024년 이후) 지표에만 쓴다. |
| `summary` | 예 | 한 문장 정의. 용어 페이지 리드와 검색에 쓰인다. |
| `easy` | 예 | 문단 2개. 수식 없이 직관과 비유로 쓴다. |
| `scale` | 아니오 | 숫자 읽는 법. 아래 별도 설명. |
| `formula` | 아니오 | `expr`(식)과 `vars`(`[기호, 설명]` 목록). |
| `deep` | 예 | 문단 2~3개. 원리, 계산 세부, 한계, 다음 단계 지표. |
| `myth` | 예 | `claim`(흔한 오해)과 `truth`(실제로는). |
| `leagues` | 아니오 | `[{lg, t}]`. KBO·NPB와 실제로 다른 점이 있을 때만 쓴다. |
| `related` | 예 | 같이 볼 용어 id. 작성된 용어만 넣는다. |
| `sources` | 예 | `[{t, u}]`. 원 출처 링크 1개 이상. |

`stubs.json`의 항목은 사다리에만 점선으로 보이는 준비 중 용어다 (`id`, `chip`, 선택 `added`). 작성하면 `stubs.json`에서 빼고 `terms/<id>.json`을 만든다.

`ladders.json`의 항목은 `name`, `hint`, `steps`(왼쪽이 기본, 오른쪽이 심화)로 이뤄진다. 한 용어가 여러 사다리에 들어가도 된다.

### `scale`

- `min`, `max`: 막대의 양 끝.
- `dir`: `high`(클수록 좋음), `low`(작을수록 좋음), `none`(좋고 나쁨이 아님).
- `fmt`: `int`, `dec1`, `dec2`, `dec3`. `dec3`은 1 미만이면 앞의 0을 뺀다 (.316).
- `unit`: 선택. `%`, `°`, ` in`. 다른 단위가 필요하면 `src/lib/schema.ts`의 `UNITS`에 먼저 넣는다.
- `avg`: 선택. `{v, t}`. 출처가 있는 리그 평균이거나 정의상 평균(100, 0)일 때만 넣는다.
- `marks`: `[{v, t}]` 구간 눈금. 라벨이 겹치지 않게 범위의 10% 이상 간격을 둔다.
- `band`: 선택. `[a, b]` 강조 구간 (예: 어택 앵글 이상적 범위).
- `note`: 선택. 기준(한 시즌, 포지션, 구종)과 ‘대략적인 구간’이라는 점을 밝힌다.

## 빌드 때 검사

`npm run build`(`astro build`)는 아래 중 하나라도 어긋나면 실패하고, 어느 파일의 어느 필드인지 알려 준다. `npm test`는 빌드 없이 같은 검사를 돌린다.

- 위 스키마: 필수 필드, 허용 값, 문단 수, 출처 URL 형식. 스키마에 없는 필드(오타)도 막는다.
- `scale`: `min` < `max`, `marks`·`avg`·`band`가 `min`~`max` 안, `marks` 사이 간격이 범위의 10% 이상.
- `related`: 작성된 용어 id만. 자기 자신, 중복, 준비 중 용어는 안 된다.
- `ladders.json`의 `steps`: 용어나 준비 중 용어 id만. 한 사다리 안에서 중복은 안 된다.
- `stubs.json`: id 중복, 이미 작성된 용어와 같은 id, 어느 사다리에도 없는 항목은 안 된다.
- 파일 이름(id)은 kebab-case.

## 쓰는 법

- **summary**: 한 문장. 처음 보는 사람이 읽고 무엇을 재는 숫자인지 알 수 있어야 한다.
- **easy**: 처음 보는 사람 기준이다. 다른 용어를 쓰면 그 자리에서 풀어 쓴다. 왜 이 지표가 필요한지(기존 지표가 놓치는 것)를 먼저 말한다.
- **deep**: 이미 아는 사람 기준이다. 계산 세부, 언제 틀리는지, 산출처별 차이, 다음 단계 지표를 쓴다.
- **myth**: 실제로 자주 보이는 오해 하나만 쓴다.
- **leagues**: 리그 상수·가중치가 따로 계산되는 경우, 공개 데이터가 없는 경우처럼 실질적인 차이만 쓴다.
- 문체는 한다체, 짧은 문장이다. 영문 약어는 처음 나올 때 한국어로 풀어 준다.
- 장식적인 표현(‘~라고 할 수 있다’, ‘주목할 점은’)은 쓰지 않는다.
- 사람이 쓴 사전처럼 사실만 적는다. 2026-10-26에 아래 버릇을 본문에서 걷어 냈다. 새로 쓸 때도 피한다.
  - 문장 끝을 ‘~하는 이유다’, ‘~가 핵심이다’로 맺기. 원인과 결과를 그냥 차례로 쓴다(‘그래서 ~한다’).
  - 지표를 사람처럼 쓰기(‘지표가 말하는’, ‘타구의 질은 정직하다’), 비유(‘움직일 재료’), ‘A라면 B는 C다’ 같은 대구.
  - ‘한 단계 더 나아간’, ‘더 많은 것이 보인다’, ‘~하는 습관이 필요하다’처럼 평가나 훈계를 덧붙이기.
- UI 문구(해요체)도 같다. 홍보 문구, 사이트 자신을 가리키는 말(‘이 핸드북이 직접 썼고’)은 쓰지 않는다.

## 저작권과 데이터

- 설명 문장은 직접 쓴다. 외부 글을 번역하거나 문장 구조를 따라 쓰지 않는다.
- 정의, 공식, 리그 평균 같은 사실은 쓰되 원 출처를 링크한다.
- 실제 선수 기록과 이름을 예시로 쓰지 않는다. 예시는 가상 수치로 쓴다.
- 확인하지 못한 수치는 쓰지 않는다. 확인한 값은 `docs/verified-facts.md`에 날짜와 함께 추가한다.

## 준비 중 용어 (stubs)

2026-10-15에 처음 준비 중이던 12개(타율, ERA, xFIP, SIERA, 타구 속도, 하드히트%, 구속, 회전수, K%, 수비율, 배트 스피드, 스윙 타이밍)를 모두 작성해 `stubs.json`은 비어 있다.

- 새 용어를 사다리에 먼저 걸어 두려면 `stubs.json`에 `{ "id", "chip", "added"(선택) }`로 넣는다. 사다리에 점선 칸으로 보이고, 홈 ‘이미 안다면’에도 `added`가 있으면 ‘준비 중’으로 나온다.
- 2026-10-23에 원문과 대조해 ERA·xFIP에는 `scale`을 붙였다(FIP도 같은 방식으로 바꿨다). 구간을 어떻게 정했는지는 `docs/verified-facts.md`의 ‘FanGraphs Library 경험칙 표’에 있다. 경험칙 표의 ‘평균’이 실제 리그 평균과 다르면 표를 그대로 옮기지 말고, 리그 평균을 기준으로 환산하거나 `scale`을 붙이지 않는다.
